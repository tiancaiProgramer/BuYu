# 网易云与QQ登录续期实现对照

维护与新增功能：tiancaiProgramer。2026-11-10核对当前源码；本次仅审计，没有修改网易云逻辑、重新认证或人为使真实账号过期。

## 网易云当前流程

1. `netease_api.dart` 初始化共享 `CookieManager + PersistCookieJar(FileStorage)`。Cookie在应用支持目录保存；本地依赖的 `persistSession` 默认开启，无Expires/Max-Age的会话Cookie也持久化，关闭应用并不会自动丢弃。服务端仍决定凭据是否有效。
2. 请求拦截器装载当前Cookie，并记录Cookie哈希及刷新版本信息。
3. 响应拦截器发现业务码301（不是HTTP重定向码）且本地有已登录账号后，尝试恢复。如果当前Cookie版本已变化，先用现有新状态重试；否则调用 `/weapi/login/token/refresh`。
4. 刷新请求使用同一个Cookie管理器，但其响应拦截器关闭再次刷新，避免刷新接口递归触发自身。返回业务码200就增加 `loginRefreshVersion`，再重发原请求。Cookie管理器会处理服务端Set-Cookie；即使Cookie内容没有变化，版本号也可表达刷新已成功。
5. 原实现中恢复抛错或刷新未成功后调用 `usc.onLogout()`，清Cookie及账号缓存。没有查到定时提前续期调度。

这是一套按请求触发的后台恢复流程，成功时用户无需重新扫码。它不能证明网易云会话永久有效，也不能证明已被服务器撤销的Cookie仍能续期；本轮没有测量真实账号的有效期。

## 与QQ 2130的关系

QQ已经具备同账号刷新成功后重试原请求、保存新状态、并发共享一次刷新和退出竞态保护；另按实际音乐密钥有效期提前续期，在回到前台及请求前补查。QQ当前用户会话实测可通过音乐密钥交换续期，未返回独立refresh_token并不代表不可续期。实际接口和返回字段必须按QQ协议处理，不能直接复用网易云的刷新地址或推定两平台凭据寿命相同。

QQ本次已经实测换新密钥、跨进程保留和音频数据读取；没有据此承诺平台撤销授权或应用完全停止超过有效期后仍能免认证恢复。

## 审计发现的网易云旧实现隐患（尚未实机复现）

- `netease_api.dart` 的恢复catch最终直接调用onLogout，刷新过程的临时网络错误也可能导致退出；QQ现实现保留最后凭据，将网络失败与明确鉴权拒绝分开。
- `netease_handler.dart` 请求侧在 `loadCookiesHash()` 结果上再次加 `loginRefreshVersion`，而该函数内部已经加过一次。刷新版本非零后，两侧比较可能一直不同，进而反复重发301请求；当前没有明确的重试次数上限。这是源码可见风险，不能写成用户已经遇到的实际故障。
- 普通拦截器没有共享续期Future，原有dio.lock代码已注释；多个并发301响应可能各自刷新。QQ现实现已经合并并发续期。

## 2131实机补充

后续优化及回退措施见[2131记录](netease-renewal-2131.md)。当前真实扫码会话资料200，但刷新400，兼容检查也400，账号仍有效。这说明有刷新代码不等于当前登录方式实际支持刷新，不能据此前源码审计把用户长期不掉线直接归因于刷新成功。2131保留有效登录并限制失败重试；尚未复现网易云自然过期。
